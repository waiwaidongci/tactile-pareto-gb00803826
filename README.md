# 触觉导览贴缺陷返修排序

循径标识工坊终检与返修组。12 人为社区服务中心制作按压成形的触觉导览贴，每班终检三个批次。终检员登记拒收件，复检台补录缺陷，工艺领班审核本轮返修顺位并发给压印、贴合和印刷工位。

CSV 合并拒收登记和缺陷复检两类记录。批次加单件编号唯一标识实物，日期填 YYYY-MM-DD。拒收登记的缺陷代码填 NONE、严重度填 0。缺陷复检的严重度为 1 至 5，代码按凸点高度不足 DOT_LOW、触觉箭头反向 ARROW_REVERSED、贴边翘起 EDGE_LIFT、对比墨层拖污 INK_SMEAR 填写。 按缺陷给出加权损失、单类和累计损失占比、涉及拒收件及分母、合并的复检行和返修动作。清单标出累计覆盖达标的缺陷，由工艺领班审核后分发给返修工位。

- 返修组把复检表的行数当成拒收件数，重测两次的贴片会被算成两件。
- 按缺陷件数直接排序后，少见但严重的读向或触感问题会排在轻微印刷缺陷之后。
- 工位收到整张异常表，需要重复商量当班优先做哪几类缺陷和做什么。

## 六个业务模块

1. 终检班次总览
2. 拒收与复检台账
3. 损失覆盖分析
4. 缺陷与返修明细
5. 工位顺位复核
6. 返修清单分发

## 按班次分开交两份原表

拒收单（`reject`，拒收登记行）与复检单（`recheck`，缺陷复检行）分开提交，复检单常先到。以班次编号（`shift`/`code`，如 `20261125-早班`、`TG-1124`）归集：

- 先到的一份立即照收（状态 `collecting`），不要求另一份在场；两份到齐后按 `lot_id + unit_id` 逐件核对，双向查找「复检无拒收」「拒收未复检」以及「复检早于拒收」，每条不符都带 `lot_id`（批次）与 `unit_id`（单件）。
- 不符时状态为 `mismatch`，按批次/单件提示补交；补交只替换对应那份原表，另一份的 `id`/SHA-256 保持不变（响应含 `kept_form`）。
- 核对通过（`ready`）才生成整班合并数据版本（先拒收后复检的稳定合并顺序），班次分析与 `POST /runs` 对该版本放行；单独一份原表的数据版本不能直接分析（409），对已通过班次的原表版本提交计算会自动解析到整班合并版本。
- 整班入库按规范化记录的 SHA-256 去重，重试不新增数据/分析版本；`POST /shifts/{key}/runs|analyze` 用「班次+整班版本+参数」派生幂等键，通用 `POST /runs` 也支持 `Idempotency-Key` 请求头。
- `POST /shifts/{key}/close`（别名 `seal`/`finish`/`lock`）在同一把班次锁与同一数据库事务内重新核对并入库，保证「核对与入库按同一组原单」完成；并发的补交与封班被串行化。封班后状态 `closed`：相同内容原单重传返回 `200` 与同一版本，内容不同返回 `409`。
- 页面「终检班次总览」顶部与「拒收与复检台账」顶部均可查「班次进度」，台账页可交单、看批次/单件不符、逐件核对、封班并跳转分析；深链 `#1/shift/{id}`。

主要接口（同时挂在根路径与 `/api` 前缀下）：`GET /shifts`、`GET /shifts/progress`、`GET /shifts/{id或编号}`、`POST /shifts`、`POST /shifts/demo`、`POST|PUT /shifts/{key}/forms[/{kind}]`（也支持 `/reject`、`/recheck`、`/uploads`、`/sheets` 等别名与 multipart 文件）、`POST /shifts/{key}/reconcile`、`POST /shifts/{key}/close`、`POST /shifts/{key}/runs|analyze`。旧的合并 CSV `POST /datasets {name,csv}` 行为保持不变；在其体里额外传 `shift` 与 `kind` 即走班次交单。


## 工作剧本

1. 08:10 终检领班在总览核对 TG-1124-01 至 TG-1124-03 三批拒收记录，三个批次各有 10 件。
2. 08:40 终检员导入 tactile-rejects-20261124.csv，其中有 30 行拒收登记及 35 行缺陷复检。
3. 09:00 工艺员以 80% 为累计损失覆盖线运行分析，批次 TG-1124-01 的 P001 凸点复检取严重度 4。
4. 09:10 结果明细确认 3 行复检被合并，凸点高度不足为 96 点，总损失为 147 点。
5. 09:25 领班确认前两类覆盖 87.07%，安排凸点重压复测和箭头换贴比对。
6. 09:40 导出审核后的明细，并将报告安排在 10:00 分发至标识返修工位。

## 算法与复核

按拒收台账中的批次与单件编号去重计算分母。同件同类缺陷复检取最高严重度，严重度 1 至 5 分别计 1、2、4、8、16 点。同件异类分别计损失。按缺陷总点数降序、同分按代码升序，把首次达到或超过累计覆盖线的缺陷纳入本轮。

空表、缺少对应拒收登记、复检早于拒收登记、非法代码或严重度会提示修复。仍有已登记但无缺陷复检的单件时，保留拒收分母，阻止批准和分发。 复核问题为「核对拒收件是否全部复检，确认截至覆盖线的缺陷可按报告所列的工位动作分派吗？」。每次分析绑定数据版本和参数，原始数据按规范化内容的 SHA-256 去重。日程针对已复核的固定结果版本，每日模式按初次投递时间每 24 小时重复。停机期间错过多次时只补一份到站内收件箱，下一次回到原时间点。

| 字段 | 含义 | 类型 |
|---|---|---|
| `lot_id` | 生产批次 | str |
| `unit_id` | 批内单件编号 | str |
| `inspection_date` | 登记或复检日期 | str |
| `record_type` | 记录类型 | str |
| `defect_code` | 缺陷代码 | str |
| `severity` | 严重度 | int |

## 启动

```sh
[ -f .env ] || cp .env.example .env
docker compose up -d --build --wait
docker compose exec -T backend python -m scripts.seed_demo
```

- Web 界面 `http://127.0.0.1:18304`
- API 文档 `http://127.0.0.1:19304/docs`
- 数据库端口 `17804`

| 账号 | 演示密码 | 工作权限 |
|---|---|---|
| analyst | analyst-demo-24 | 导入 CSV、运行分析、导出工作稿 |
| reviewer | reviewer-demo-24 | 复核、设置和停止投递、导出 |
| viewer | viewer-demo-24 | 浏览结果、导出已批准的报告、查收投递 |

原生 HTML/CSS/JavaScript 前端与 Nginx、FastAPI、Python worker、PostgreSQL 16 和 Redis 组成五服务 Compose。`backend/src/services/domain.py` 存放业务算法，`domain.json` 定义字段与验收口径，`frontend/src/pages` 为业务页面。更新任一侧源文件后，用 `docker compose up -d --build` 重建对应镜像。`backend/src/constants/enums.py` 和 `frontend/src/constants/enums.js` 定义角色及运行状态。`.env` 支持前端、API、数据库端口、演示 seed 开关和 JWT 密钥。首次部署到非演示环境时更换演示身份及 JWT/数据库凭据。

`docker compose down` 停止服务并保留数据卷。现场数据和演示结果可以在各自版本中并存。
